# MCP v5 八菜单能力差距与任务精细化（2026-10-29）

本次核查对象是任何独立 Git 项目使用同一套 mcp-probe-kit 的行为。每个项目的 SQLite 研发数据互相隔离，不能为了适配界面迁移或重建其他项目的任务。

| 菜单 | 已有能力 | 尚未完成的产品能力 |
| --- | --- | --- |
| 工作台 | Git、愿景、路线图、下一任务、工作项进度 | 风险、阻断决策、外部 Gate、阶段目标的整体追踪 |
| 需求管理 | PRD、Feature 三阶段 SQLite 规格与需求关联 | Idea 评估、审核、批准与影响范围一体化展示 |
| 技术架构 | 架构/ADR 文档、变更类型区分 | 真实代码依赖、变更影响与待审决策关联 |
| 任务管理 | 真实任务状态、详情、依赖、交付证据 | 任务粒度审核、父子拆分建议、各类合法计划的视觉一致性 |
| Bug 管理 | SQLite Bug 列表与详情 | 严重度、复现、修复和回归 Gate 的关联追踪 |
| 历史会话 | SQLite History 检索 | 关键决策、交接、关联任务和遗留问题的结构化导航 |
| 研发指南 | 当前开发阶段及受控调用指南 | 结合实时 Gate 与风险给出下一合法操作 |
| 设置 | 项目级 MCP 参数、安全配置 | 配置变更差异、健康检查与真实连接测试 |

八个导航入口并不等于这些能力均已交付。现有后端动作也不等于前端已具备完整管理操作。工作台不应直接修改 SQLite、伪造 Gate 或跳过 Owner 精确审批。

## 不同项目的一致界面

ReleaseWorkPlan、FeatureTaskPlan 和 ReleasePlan 是不同的合法计划来源。以前整版计划使用浅色 task-card，Feature 计划回退到深色 simple-task。现在两个数据分支必须调用同一个任务卡片渲染器，既显示阶段分组和待审限制，也保证字体对比、移动端适配一致。不能让其他项目修改业务数据来适应组件。

## 新任务粒度规则

- 新叶子任务目标为 30–60 分钟，只有一个可独立验收成果。
- 60–120 分钟允许有说明的例外，必须写明为何不能再安全拆分。
- 超过 120 分钟的新微任务提案，严格审核退回拆分。
- 新 Feature 提案默认采用微任务审查。新整版计划可采用 task-detail-v2 严格配置；旧已冻结 v1/legacy 任务不自动修改或作废。
- 时间不是唯一指标。数据资格、业务实现和独立的验收交付如果是不同的成果，应拆分。单一成果的实现、失败验证和证据可以同属一个任务，不必机械拆分。
- 任务必须明确需求来源、单一验收目标、设计、依赖、文件范围、输入输出、正反场景、Gate 和停止条件。

## 多项目验收门禁

至少测试已有整版冻结任务项目、仅有 Feature 待审计划项目和全新空项目。每种均验证 2560px、1440px、768px 与 390px 屏宽的任务状态、卡片对比度、详情、限制提示和空状态。外部用户项目实例尚未实际回归时，不得宣称外部项目验收通过。
