FIELD-TESTED DEVELOPMENT · v5.0.0 SOURCE

v5 最佳实践：让 Agent 真正持续交付软件

v5 重大更新：研发管理仅通过 SQLite + DevControl。v4 文件式 Plan / Spec / History 不再支持；旧流程只保留历史资料。查看 v5 正式架构与迁移状态。

我们在 Neyna 的长期实战中发现：研发效率并不只靠更强的模型，而是让每次修改都拥有真实来源、审批边界、可恢复状态和可核验的测试证据。v5 把这些要求变成一套可以长期运行的项目研发流程。

01 · PLAN

先审核，再开发

评估完整需求与依赖，提交计划草稿，独立复审后由 Owner 明确批准，不靠一句“继续”扩张授权。

02 · DELIVERY

逐任务、真测试

冻结路径、领取租约、实际编码、独立检查，再用与提交绑定的真实 Gate 判定完成。

03 · CONTINUITY

跨会话不断档

任务状态放 DevControl，用户原话与交接放 History，长期通用经验才进入可选 Memory。

1. v5 最重要的变化：明确谁对结果负责

DevControl 是项目管理与约束工具，不是替 Agent 编码或审核的“自动开发者”。 这一点是长期实践反复验证出来的边界。

角色应该做什么不能混淆
Owner决定产品取舍、批准准确的计划或变更哈希口头继续不等于允许修改所有文件
Agent审读需求、设计方案、独立复审、编码、真实测试不能把 DevControl 的返回值当作业务正确性审核
DevControl记录任务与审批、冻结文件范围、管理租约、核验 Gate不代替 Agent 写代码、执行业务 SQL 或独立评审
History Session保存用户原话、决策、发现、阻碍及跨窗口交接不是任务账本，也不是 Qdrant Memory

2. 新对话不要重新开工：先恢复已存在的项目

正确的第一步是通过 history_session_bootstrap 恢复现有会话，然后核实真实 Git 分支、HEAD、未提交文件、需求、ADR、DevControl 任务、租约和环境。必要时通过 history_session_search / history_session_read 找到旧决策。

  1. 确认业务项目的 Git 根目录，不要把 MCP 源码仓库误当成业务项目。
  2. 阅读 AGENTS.md、Skill、正式需求和架构，不重复初始化冻结计划。
  3. 调用 devcontrol next、list、execution-contract 确认下一项合法任务及旧租约。
  4. 先检查真实可执行环境、网络、数据库和设备，不把精简 PATH 误认为 SDK 未安装。
  5. 结束前调用 history_session_checkpoint，留下真实状态与下一步。

3. 研发闭环：从真实需求到 Verified

任务不是一个标题，而是一份受控执行合同。先检查来源、成功/失败场景、依赖、输入输出、allowedPaths、真实测试和停止条件；随后才能领取。

Plan审核完整需求
Approve冻结 Owner 决定
Claim领取合法范围
Build实现 + 真测试
Verify证据 + Gate

两个绝不能省略的审批层次

plan-review → plan-propose → plan-approve 依次完成检查、待审提案和按哈希授权；草稿不是可执行任务。已批准任务通过 next → execution-contract → claim → renew 执行，真实 Git 提交后以 complete → report → verify 验收。

# 下列是命令形式示例，不表示自动拥有任务授权
probe devcontrol next --project-root .
probe devcontrol execution-contract --project-root . --json '{"id":"APPROVED-TASK-ID"}'
probe devcontrol claim --project-root . --json '{"id":"APPROVED-TASK-ID","agent":"developer-id","ttlSeconds":3600}'
# 编码、独立审查、真实测试并仅提交已获准文件
probe devcontrol check --project-root .
# 根据返回的 leaseToken 执行 complete / report / verify

Commit 不等于 Verified。 即便代码已提交，未执行 Gate、缺依赖或测试证据不足，都必须保留真实未完成状态。

4. 新想法和范围变更不能随意打断开发

新需求先用 idea-capture → idea-assess → idea-review → idea-decide 判断它属于当前已批准的合同、后续版本还是应该拒绝。这不是“所有新想法都不接”，而是结合风险、价值和依赖决定适当阶段。

  • 超出冻结文件范围：停止越权修改。走 release-work-scope-review、release-work-scope-stage、release-work-scope-independent-review、release-work-scope-approve 等精确流程。
  • 已经领取的任务：使用受控暂停/恢复流程保留合法租约、已提交结果和用户原有 dirty，不直接 reset/stash 或跳过 Git Hook。
  • API/Schema/安全架构变化：通过 artifact-stage、artifact-independent-review、artifact-approve 及 artifact-check 控制正式工件哈希。

5. 真实 Gate：测试必须对应真实风险

场景真正需要的验证不能用来代替的内容
Go HTTPgo_http_integration、实际请求、错误路径和持久化只通过静态编译或模拟 HTTP
Flutterflutter_test、真实 Flutter SDK 测试和分析空测试或假的 Flutter runner
PostgreSQL获授权的测试库、真实权限/RLS/事务回滚证据未执行的 SQL 或直接在生产库试错
iPhone 真机ios_device_e2e、实际系统授权/拒绝/恢复和设备证据模拟器、UI 截图或单元测试冒充真机
文档和发布真实文档构建与检查、必要 CI 和制品验证只修改 README 或仅提交 Git

没有真实运行器时，应标记阻塞、Not Run 或失败，而不是修改验收条件。可以合法推进其他没有该依赖的**已批准任务**。

6. 多任务推进：提高吞吐量，不降低标准

长期研发不应该每次只交付半项；当依赖、环境和质量门禁允许时，可以把多个已批准的小任务分组处理。Neyna 试点曾采用约 10～12 项为目标、分组复核的节奏，这只是工作方式，不是产品硬规定。

  • 每项分别确认任务合同、租约、合法提交、实际测试和 verify；不能把批次 Git Commit 当作批次验收。
  • 优先推进依赖就绪、相互不冲突的任务；高风险和跨端任务增加独立复审。
  • 长命令设置超时，检查进程是否真的结束；未结束的测试不能宣称通过。
  • 阻塞时报告真实的 Verified 数与未完成原因，不为了凑数量绕过门禁。

7. 任务、会话和长期经验各自有权威存储

数据类型权威存储用途
任务/审批/证据项目 SQLite dc_*DevControl 的工作状态与审计
会话原话/交接Git/Node22+ 项目默认 SQLite hs_*History API 跨会话恢复；旧 Markdown 可迁移
跨项目可复用经验可选 Qdrant Memory检索经验证的方法，不代替当前任务记录
正式需求/架构/业务数据项目 Git 规范文档 / 业务自己的数据库不能混进 DevControl 的研发账本

8. Neyna 实战反复提醒我们的误区

  1. 误把 DevControl 当成“独立审核者”——实际需要 Agent 自行评估代码与风险。
  2. 收到新想法立刻插入开发——应该先评估是否影响冻结任务与依赖计划。
  3. 范围不匹配就随手修改文件——必须先提交最小修订并复审，再继续执行。
  4. 真机不可用却宣称已验收——只能保留待测和阻塞状态。
  5. 跨聊天窗口重新生成整版计划——先从 History 和实际 SQLite 任务恢复。
  6. 把用户原先的 dirty 用 git add . 混入任务——应只暂存获批文件并保留所有权。
  7. 将 GitHub 推送误认为 npm 5.0.0 已发布——源码、文档、构建、正式发布是不同阶段。

9. 一轮研发结束时的交付清单

  1. 目标：本轮完成了哪些已批准任务，是否存在获批变更。
  2. 代码：准确的 Git 分支、Commit SHA、修改路径和可观察业务效果。
  3. 证据：实际运行的命令、平台、通过/失败/未运行及真机独立证明。
  4. 状态：按 DevControl 区分 In Progress、In Review、Verified 与阻塞。
  5. 保护：保留的其他用户改动、风险和必须处理的环境问题。
  6. 交接：history_session_checkpoint 保存用户原话、决策、测试和下一可执行任务，并核查调用成功。

成功标准：换一个 Agent 或新开聊天，不需要猜测“上轮到底做完没有”；Owner 能追溯为什么做、依据什么批准、改了什么、哪些验收真正通过。
